# 실제 Supabase 연결 후 확인 순서

**아직 실행하지 않은 운영 환경 테스트입니다.** 실제 학생 자료를 받기 전에 별도 개발 프로젝트에서 진행하세요. 아래 A/B/부장/임원은 테스트 역할의 명칭이며 운영 DB에 자동 생성되는 가짜 계정이 아닙니다. 타인의 실제 학생증으로 시험하지 마세요.

## 준비

- migration 001~008 또는 새 설치용 production-fresh.sql 적용.
- `.env.local`/서버 환경변수 설정, 현재 학년도 초기화, `npm run db:check` 전 항목 PASS.
- README bootstrap 절차로 공통 가입을 거친 최초 SUPER_ADMIN 및 부장/회장단 인증 담당자 설정. 처리한 사진이 삭제됐는지 확인.
- 브라우저 프로필을 분리: 학생 A, 학생 B, 승인 가능한 부장, 전달 담당 임원. 테스트 학년도·운영 담당자 결정.
- 실제 서버 주소로 접속. 현재 정적 화면용 chatgpt.site 링크에서 검사하지 않음.

## 요청한 전체 흐름

| 순서 | 수행할 작업 | 화면·DB에서 기대하는 결과 |
|---|---|---|
| 1. 회원가입 | 공통 가입 화면에 A의 이름·학번·6자리 PIN 입력 | role 선택 없음. PIN 원문이 DB에 없고 `pin_credentials`에는 `scrypt$…` 해시만 존재 |
| 2. 학생증 제출 | A 본인의 검증용 사진 제출 | 인증 대기. `student_verifications`에 ACCOUNT_PENDING, private bucket에 객체 1개. 분실물 기능은 아직 비활성 |
| 3. 관리자 승인 | 부장/회장단으로 A 학생증 확인·승인 | VERIFIED. 원본 객체가 Storage에서 없어지고 `verification_uploads`는 DELETED, object_path=null. 앱 알림 생성 |
| 4. 로그인 | A 로그아웃 후 같은 이름·학번·PIN으로 로그인 | 본인 내역 표시. 새로고침·다른 기기에서도 동일 DB 기록 |
| 5. 관리자 권한 확인 | 후보 테스트 학생은 사전 등록 후 동일 가입·사진 승인. A는 일반 학생으로 유지 | 승인 전 관리 메뉴 없음. 승인 후 후보 학년도·이름·학번이 모두 맞는 계정만 role 활성화. A의 `/admin` 직접 접근은 차단 |
| 6. 분실물 등록 요청 | A가 사진·물품명·종류·장소·날짜 입력. 기타 선택 시 상세 입력 | 등록 요청 완료 안내. 아직 공식 목록에는 없음. `item_submission_requests` 생성 |
| 7. 복지부 승인 | 실물을 안전생활부실에서 받은 후 ‘실물 확인’, 사진 검수·보관번호 입력·승인 | 실물 확인 전 승인 불가. 승인 후 items/item_images/item_private_details/item_history 생성 |
| 8. 목록 표시 | A/B가 찾기 화면 새로고침 | 실제 등록 물품과 발견 장소·보관 위치 분리 표시. 내부 보관번호·등록 학생 정보는 일반 목록에 없음 |
| 9. 찾아가기 요청 | B가 공개 사진에 없는 특징 입력 | B 마이에 대기 안내. A는 B의 특징·개인 요청을 볼 수 없음 |
| 10. 수령 승인 | 부장/회장단이 B 특징 확인·승인 | B에게 일회성 수령번호와 시간 선택 안내. 관리자라도 학생 본인 요청 기능 이용 가능 |
| 11. 시간 예약 | 지정 임원이 가능 시간 등록. B가 10분 시간·두 장소 중 하나 선택 | 합쳐진 예약 가능 시간만 노출. 예약 전에는 임원별 개인 일정 비공개 |
| 12. 담당 임원 배정 | 예약 확정 후 B와 배정 임원 화면 확인 | 가능하면 복지부 우선 배정. B에게 담당자 표시. 임원은 본인 배정만 보며 내부 번호·학생 이름/학번·수령번호 확인 |
| 13. 수령 완료 | 임원이 B의 번호 확인 후 실물 전달 체크·완료 | 물품 RETURNED, 예약 COMPLETED, 반환 시각/담당자/학생·history 기록, 수령번호 hash/ciphertext 제거, 완료 알림 |

각 행의 실행 시각·성공 여부·실패 화면만 기록하고 PIN, 세션 토큰, 학생증 원본은 테스트 보고서에 붙이지 마세요.

## 개통 전에 추가로 확인할 차단·실패 조건

1. **인증 전 권한:** 이름/학번이 후보와 같아도 미승인·거절·후보 취소·다른 학년도라면 관리 권한 없음. 일반 임원과 최고관리자의 학생증 이미지 API 직접 호출도 차단.
2. **역할 부여·회수:** 복지부가 회장단을 지정하려 하면 실패. 회장단이 최고관리자를 지정해도 실패. 권한 해제 후 같은 세션으로 관리 URL/API를 다시 호출해 차단 확인. 학생 기능과 이전 기록은 유지.
3. **RLS:** Publishable Key로 private 테이블 SELECT/INSERT/UPDATE/DELETE와 업무 RPC 호출을 시도해 차단 확인. 기존 프로젝트의 광범위한 정책도 점검. service_role 키로 한 테스트는 학생 RLS 검증이 아님.
4. **로그인 제한:** 같은 이름/학번으로 연속 실패 시 제한 적용. PIN은 클라이언트·서버 로그에 출력되지 않음. HTTPS 쿠키에 HttpOnly/Secure/SameSite 확인.
5. **중복 예약:** 실제 서로 다른 기기/브라우저에서 같은 마지막 슬롯을 동시에 예약. 담당자 1명당 슬롯 1개만 확정. 실패한 쪽은 다른 시간 선택 가능. 로컬 직렬 테스트만으로 대체하지 않음.
6. **미수령:** 예약 종료 후 담당자가 미수령 처리. NO_SHOW 이력·알림이 남고 B가 다시 예약 가능. 종료 전 미수령 처리와 다른 임원의 처리는 차단.
7. **코드 재사용:** 완료된 예약·번호로 수령 완료 API를 다시 호출해 실패 확인. 잘못된 코드도 실패.
8. **학생증 거절·삭제 장애:** 거절해도 원본 삭제. 별도 개발 환경에서 Storage 오류를 유도한 뒤 DELETION_PENDING 유지, 이미지 열람 차단, 연결 복구 및 maintenance 후 DELETED 확인. 운영 bucket 정책을 임시로 공개하지 않음.
9. **14일 표시:** 개발 DB의 공식 승인 시각을 14일 이상 이전으로 설정한 미반환/미승인 소유 물품에 장기 미수령 표시. 자동 삭제되지 않음. 테스트 변경은 운영 데이터에 하지 않음.
10. **직접 등록:** 관리자가 사진·발견 시간·내부 번호·실물 확인을 입력해 바로 공개. audit log에 등록자/시각. 중복 보관번호로 실패하면 부분 등록이 남지 않음.
11. **정기 작업:** 5분 실제 스케줄이 호출되는지 확인. 예약 30분 전 알림이 한 번만 생성, 만료 사진·삭제 재시도 처리 확인. 잘못된 CRON_SECRET은 401.
12. **학년도 인계:** 개발 프로젝트에서 진행 중 요청을 마무리한 뒤 인계. 물품/과거 로그 유지, 이전 관리자·후보 만료, 현재 학번 재인증 필요. 기존 UUID 계정 유지. 운영 연도는 테스트 삼아 바꾸지 않음.
13. **사진·모바일:** 실제 휴대폰의 JPG/PNG/WebP와 최대 용량 경계 파일 시험. 서버 호스트 요청 크기 제한·이미지 회전·민감 정보 가림 확인. 모바일에서 가입/목록/예약/관리 화면 사용.
14. **연결 실패:** 개발 서버에서 잘못된 프로젝트 키·미설정 학년도·누락 migration을 시험하면 연결 준비/실패 상태. 성공 또는 가짜 목록을 표시하면 개통 보류.

## 완료 기준

위 전체 흐름과 차단 조건을 모두 확인하고, 실제 원본 삭제·동시 예약·외부 정기 실행 결과를 기록해야 합니다. 이 문서가 존재하거나 로컬 테스트가 통과했다는 이유만으로 운영 검증을 완료 처리하지 않습니다.

## Secret Key 설정 확인

- 새 설치에서 SUPABASE_SECRET_KEY만 사용하고 이전 SUPABASE_SERVICE_ROLE_KEY는 제거한다.
- SUPABASE_SETUP.md B의 대시보드 체크리스트로 같은 프로젝트의 URL/Publishable/Secret Key를 설정한다.
- SQL 적용 및 학년도 초기화 후 `npm run db:check`가 모두 PASS인지 확인한다.
- 서버를 재시작/재배포하고 기존 전체 사용자 흐름을 실행한다. 실제 Supabase 연결은 로컬 격리 테스트와 별도로 확인한다.
