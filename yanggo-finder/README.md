# 양고 찾기 — 기존 프로젝트 운영 기능 수정본 v0.4.0

2026-09-23. 기존 Next.js 프로젝트를 수정했습니다. 색상·카드·검색 화면·페이지 경로·모바일 메뉴·폰트는 유지했습니다. 최근 시연 HTML과 원본 ZIP의 HTML은 같은 파일임을 확인했습니다.

**구현 코드와 로컬 검증을 제공하는 단계입니다. 실제 Supabase 프로젝트 연결·마이그레이션 적용·운영 서버 배포는 수행하지 않았습니다. 정적 공개 화면만 배포된 상태입니다.** 연결 정보가 없으면 빈 목록과 연결 준비 안내가 나오며 가입·등록·예약을 받지 않습니다. 기존 HTML은 과거 시연물입니다. 이 버전은 Next.js 서버로 실행해야 합니다.

## 실행

Node.js 24.x. 프로젝트 폴더에서:

```bash
npm ci
npm run dev
```

`http://localhost:3000`을 엽니다. 서버 환경변수가 없는 상태에서도 화면과 연결 준비 상태를 확인할 수 있습니다.

```bash
npm run typecheck
npm test
npm run build
npm start
```

브라우저 통합 테스트는 별도로 실행합니다. **테스트 전용 로컬 PostgreSQL(PGlite)·Storage 어댑터를 사용하며 실제 Supabase에 접속하지 않습니다.**

```bash
npx playwright install chromium
npm run build
node tests/browser.mjs
```

테스트 계정과 파일은 테스트 프로세스에만 생성되며 종료하면 사라집니다. 운영 코드에는 seed, 역할 전환기, 성공을 흉내 내는 Mock 처리가 없습니다.

## Supabase 연결

1. 운영 전 먼저 별도 개발 Supabase 프로젝트를 준비합니다.
2. `.env.example`을 `.env.local`로 복사하고 아래 값을 설정합니다. `NEXT_PUBLIC_` 두 값 외에는 **서버에만** 설정합니다. Git이나 채팅에 비밀키를 올리지 마세요.

| 변수 | 용도 |
|---|---|
| `APP_ORIGIN` | 개발은 `http://localhost:3000`, 운영은 실제 HTTPS 주소. 끝에 경로를 붙이지 않음 |
| `NEXT_PUBLIC_SUPABASE_URL` | 연결할 Supabase 프로젝트 주소 (공개 가능) |
| `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` | 공개 키. 연결 점검의 직접 접근 차단 검사에 사용 |
| `SUPABASE_SECRET_KEY` | 서버 전용 Supabase 키. sb_secret_ 형식의 Secret Key |
| `PIN_PEPPER` | PIN 해시용 독립 비밀값. 최소 32자 |
| `DATA_ENCRYPTION_KEY` | 수령번호 AES-256-GCM 암호화용 32바이트 키의 64자리 hex 표현 |
| `CRON_SECRET` | 정리·알림 작업 호출용 독립 비밀값, 최소 32자 |

키 생성 예시:

```bash
node -e "console.log(require('node:crypto').randomBytes(32).toString('hex'))"
```

세 비밀값은 각각 새로 생성합니다. PIN_PEPPER와 DATA_ENCRYPTION_KEY를 잃거나 무계획하게 바꾸면 로그인/수령번호 복호화가 깨집니다. 운영 담당자가 안전하게 보관하고 키 교체 절차를 정해야 합니다.

3. `supabase/migrations/`의 파일을 **이름 순서대로** 적용합니다. 새 DB에는 001~008 전체 또는 production-fresh.sql 한 번, 기존 DB에는 미적용 migration만 적용합니다. 두 설치 방식을 중복 실행하지 않습니다. Supabase CLI를 사용하면 프로젝트 연결 후 `supabase db push`로 관리할 수 있습니다. 이미 반영된 파일을 SQL Editor에서 반복 실행하지 마세요.
4. 기존 DB의 사용자/역할 중복이 새 unique index와 충돌한다면 기존 기록을 검토해 정리해야 합니다. 삭제로 우회하지 마세요.
5. `student-verifications`, `item-photos` 버킷이 private인지 확인합니다. 005 마이그레이션이 생성합니다. 기존 프로젝트의 광범위한 Storage 정책이 두 버킷 접근을 허용하지 않는지도 확인합니다.
6. 아래 절차로 최초 운영 관리자와 학생증 확인 담당자를 지정합니다.
7. 정리·알림 스케줄을 연결하고, 개발 환경에서 두 학생과 두 임원으로 실제 접근 차단·동시 예약·삭제 실패 복구를 점검한 뒤 운영 프로젝트에 적용합니다.

## 로그인과 RLS 구조

요청대로 **이름 + 학번 + 6자리 PIN**을 사용합니다. Supabase Auth 이메일 로그인을 흉내 내지 않고, 별도의 서버 세션을 사용합니다.

- PIN은 무작위 salt + 서버 pepper + scrypt로 해시합니다. 원문을 DB에 저장하지 않습니다.
- 이름/학번 조합별 15분 내 5회 제한. 정상 로그인 시 해당 조합의 횟수를 초기화합니다. 네트워크 단위 제한도 둡니다.
- 브라우저는 무작위 세션 토큰을 HttpOnly·SameSite=Strict 쿠키로 받고, DB에는 토큰 해시만 저장합니다. 운영 쿠키는 Secure입니다. 세션은 12시간입니다.
- 모든 앱 테이블에 RLS/FORCE RLS와 명시적 restrictive 정책이 적용됩니다. `anon`, `authenticated`의 직접 테이블·업무 RPC 접근은 차단합니다. 브라우저에 Supabase 키/클라이언트를 제공하지 않습니다.
- 서버가 세션으로 actor를 확정하고, SQL 함수가 현재 학년도 인증·역할·소유권·담당자 조건을 다시 검사합니다. 클라이언트가 보낸 user ID·권한·코드 해시는 신뢰하지 않습니다.
- 학생의 데이터는 자신의 요청만 반환하고, 일반 목록에 보관번호·소유 확인 답변·학생증을 포함하지 않습니다.
- 이 구조는 **Supabase Auth JWT의 `auth.uid()`를 사용하는 클라이언트 직결 정책과 다릅니다.** 향후 Auth JWT 방식으로 변경할 때는 지금의 서버 경로를 유지한 채 새 RLS 정책과 접근 테스트를 함께 설계해야 합니다. 단순히 테이블 권한을 열면 안 됩니다.

RLS 참고: https://supabase.com/docs/guides/database/postgres/row-level-security
Node.js 암호화 API: https://nodejs.org/api/crypto.html

## 공통 가입·권한 구조

일반 학생·임원·부장·회장단 모두 `/login`의 같은 가입/로그인을 이용합니다. 승인 대기 계정은 자신의 인증 상태와 알림만 확인할 수 있고, 학생증 승인 이후 학생 기능이 활성화됩니다. 관리자는 학생 기능에 관리 기능이 추가됩니다.

| 역할 | 학생증 열람·승인 | 관리자 역할 부여·회수 |
|---|---|---|
| STUDENT | 불가 | 불가 |
| COUNCIL_MEMBER | 불가 | 불가 |
| WELFARE_MANAGER | `is_head=true`인 부장만 | 학생 ↔ COUNCIL_MEMBER |
| PRESIDENT_TEAM | 가능 | 학생·COUNCIL_MEMBER·WELFARE_MANAGER 범위 |
| SUPER_ADMIN | 역할 자체로는 불가 | 웹에서 SUPER_ADMIN 이외 역할 관리. 최고 관리자 변경은 서버 전용 절차 |

역할 부여 대상은 가입·현재 학년도 학생증 인증이 완료된 UUID 계정이어야 합니다. 본인의 권한 변경은 막습니다. 역할 변경은 이전 role 행을 만료시키고 새 행을 생성하며 감사 기록에 actor·대상·이전/새 역할·시간·학년도·부장/전달 권한을 남깁니다. 미처리 전달 예약이 있는 담당자의 역할 변경은 먼저 예약을 정리한 뒤 가능합니다.

`admin_allowlist`는 RLS와 직접 접근 권한 차단을 적용한 비공개 후보 테이블입니다. 이름·학번·학년도 일치 **및 사진 제출·승인** 이후에만 승인 트랜잭션 안에서 권한을 활성화하고 `claimed_user_id`, `activated_at`을 기록합니다. 로그인이나 가입만으로 권한을 주지 않습니다. 이미 인증된 계정은 후보 등록 대신 ‘관리 → 관리자 관리’에서 선택합니다. 후보 취소와 권한 해제는 구분되며, 해제해도 학생 계정은 유지됩니다.

## 최초 관리자 설정 — 별도 계정을 만들지 않음

서비스 키를 관리하는 **학교 시스템 운영 담당자**가 수행합니다. 서비스 키·PIN을 프론트엔드, 저장소, 채팅에 넣지 마세요. 공통 가입을 건너뛰어 이름·학번·PIN만으로 관리자 계정을 생성하던 기존 bootstrap 함수는 007에서 제거했습니다.

1. 001~008 migration과 서버 환경변수를 적용한 Next.js 서버를 실행합니다.
2. 최초 설치 때만 현재 학년도를 초기화합니다. 이미 현재 학년도가 있으면 실행하지 않습니다.

```bash
npm run bootstrap
```

위 명령은 표준입력 JSON을 읽습니다. 아래 각 JSON은 **서로 다른 단계에서 한 번씩** 입력하며, 입력 후 EOF(터미널의 Ctrl+D)를 보냅니다. UUID 자리에는 DB에서 확인한 실제 ID를 넣습니다. 비밀번호는 이 절차로 입력하거나 변경하지 않습니다.

```json
{"mode":"initialize-year","year":2026}
```

3. 최초 SUPER_ADMIN이 될 사람도 다른 학생과 동일하게 웹에서 이름·학번·6자리 PIN·학생증으로 가입합니다. 이 시점에는 인증 대기이며 관리자 권한이 없습니다.
4. 학교 운영 담당자가 실제 학생 신원을 대면 확인한 뒤, DB의 가입 계정 UUID(`users.id`)를 확인하고 다음을 실행합니다. **현재 학년도에 이미 활성 SUPER_ADMIN이 있으면 최초 설정을 거부합니다.**

```json
{"mode":"first-super","userId":"실제 가입 계정 UUID","identityReviewed":true}
```

5. 최초 부장 또는 회장단 후보를 비공개 DB에 등록합니다. SUPER_ADMIN이 같은 로그인 화면으로 로그인하여 ‘관리 → 관리자 관리 → 가입 전 관리자 후보 사전 등록’을 사용해도 됩니다. 서버에서 등록할 경우:

```json
{"mode":"candidate","superId":"위 SUPER_ADMIN UUID","name":"실제 이름","number":"실제 5자리 학번","role":"WELFARE_MANAGER","head":true}
```

6. 해당 부장/회장단이 같은 가입 화면에서 학생증을 제출합니다. DB에서 그 요청의 `student_verifications.id`를 확인합니다. 학교 담당자가 실제 신원을 대면 확인한 뒤 최초 인증 담당자를 아래 서버 절차로 승인합니다.

```json
{"mode":"first-verifier","superId":"위 SUPER_ADMIN UUID","verificationId":"실제 인증 요청 UUID","identityReviewed":true}
```

**이 단계만 최초 승인 담당자가 없는 문제를 해결하기 위한 서버 전용 예외입니다.** 유효한 학생증 제출, 현재 학년도, 정확히 일치하는 활성 부장/회장단 후보가 필수입니다. 승인 가능한 부장/회장단이 이미 한 명이라도 있으면 이 절차를 거부합니다. SUPER_ADMIN의 웹/API에는 학생증 보기·승인 권한을 열지 않습니다. 학교 담당자가 신원을 확인하지 않은 상태로 `identityReviewed:true`를 입력하면 안 됩니다.

7. 이후 모든 학생·관리자 후보는 부장/회장단이 웹의 ‘관리 → 학생 인증’에서 승인합니다. 후보가 일치하면 같은 트랜잭션에서 role이 추가됩니다. 누구나 누를 수 있는 초기 관리자 버튼, 별도 관리자 가입·로그인 화면은 없습니다.
8. 서버 절차도 처리 직후 원본 사진 삭제를 시도합니다. 삭제 실패는 큐에 남고 정기 작업이 재시도합니다. 스크립트의 실패 건수와 DB의 삭제 상태를 확인합니다.

SUPER_ADMIN을 추가하거나 해제할 때도 **기존에 가입·현재 학년도 인증된 다른 학생**만 대상으로 합니다. 학교 운영 담당자가 서버에서 다음을 실행합니다. 웹에서 `role:SUPER_ADMIN`을 보내도 거부합니다. 자기 자신을 해제할 수 없어 마지막 최고 관리자를 실수로 없애지 않습니다.

```json
{"mode":"super-role","superId":"기존 SUPER_ADMIN UUID","userId":"인증된 대상 UUID","grant":true,"confirm":true}
```

`grant:false`는 대상의 최고 관리자 권한을 회수하고 학생 계정으로 유지합니다. 모든 변경은 감사 로그에 남습니다.

새 학년도 전환 후에는 기존 계정으로 로그인하여 현재 학번과 학생증을 재제출합니다. 새 계정을 만들지 않습니다. 그 후 4~7 단계로 새 학년도 최초 운영자·인증 담당자를 활성화합니다. 이전 후보·관리자 권한은 자동 승계되지 않습니다.

## 학생증 삭제와 주기 작업

승인·거절 트랜잭션에서 `DELETION_PENDING`으로 전환하고 웹 서버가 즉시 Storage 삭제를 요청합니다. 성공한 경우에만 DB 경로를 지우고 `DELETED`로 기록합니다. 실패는 삭제 재시도 중으로 표시합니다. 승인된 사진은 삭제 작업이 실패해도 이미지 API로 다시 열람할 수 없습니다.

`GET /api/maintenance`에 `Authorization: Bearer <CRON_SECRET>`을 붙여 **5분 간격**으로 호출하도록 운영 스케줄러를 연결합니다. 이 코드가 외부 스케줄러를 자동 생성한 것은 아닙니다.

- 실패한 학생증 삭제 재시도
- 72시간 넘은 미처리 학생증 만료 및 재제출 안내
- 1시간 지난 미연결 업로드 삭제
- 30분 이내 수령 예약 알림(한 번만)
- 만료 세션·오래된 로그인 제한 기록 정리

`ops/vercel-cron.example.json`은 스케줄을 지원하는 배포 환경용 예시입니다. 사용 중인 Vercel 요금제/스케줄 제한을 확인한 뒤 적용하거나 같은 주기의 외부 스케줄러를 사용합니다. 수동 점검은 `npm run maintenance`로 가능합니다. **스케줄러가 연결되지 않으면 재시도·예약 임박 알림의 실행을 보장할 수 없습니다.**

## 실제 운영 흐름

등록 요청 → 안전생활부실 전달 → 복지부 실물 확인 → 공개 정보·사진 검수 → 보관번호 입력 및 승인 → 공식 목록 공개 → 본관 중앙 현관의 잠금형 분실물함 보관.

찾아가기 → 비공개 특징 검토 → 승인 및 일회성 수령번호 생성 → 10분 시간과 두 장소 중 선택 → 가능한 복지부 임원 우선 배정 → 담당 임원의 번호 확인 → 실제 전달 체크 → 수령 완료.

- 예약 취소는 기록을 남깁니다. 학생은 다시 시간을 선택할 수 있습니다.
- 담당 임원만 자신의 배정을 처리합니다. 미수령은 10분 예약 시간이 끝난 뒤 가능합니다. 기록은 NO_SHOW로 남고 재예약이 가능합니다.
- 수령 완료는 DB 트랜잭션으로 물품·예약·요청·번호·이력·알림을 함께 변경합니다.
- 14일 기준은 **공식 승인 시각**입니다. 승인된 소유 요청이 없는 미반환 물품(STORED/CLAIM_PENDING)을 장기 미수령으로 표시합니다. 자동 폐기하지 않습니다. 최초 승인 시각은 연도 인계 때도 유지됩니다.
- 한 번의 시간 구간 등록은 최대 4시간, 10분 단위입니다. 두 수령 장소 모두 대응 가능한 시간만 등록합니다.

## 학년도 인수인계

관리 → 인수인계에서 진행합니다. 미처리 등록 요청·활성 수령 요청을 먼저 종료하고 실물 수량을 확인해야 합니다. 미수령 물품의 현재 관리 연도만 변경하고 최초 등록 연도·이력·반환 기록은 보존합니다. 기존 역할과 로그인 세션은 만료합니다.

전환 직후에는 기존 학생회가 새 학년도 권한을 가지지 않습니다. 학교 운영 담당자가 위 부트스트랩 절차로 새 학년도 최초 운영자와 학생증 확인 담당자를 지정해야 합니다. 이후 학생은 기존 이름·학번·PIN으로 로그인해 현재 학번과 학생증으로 재인증합니다. 관리자에서는 학년도를 선택해 지난 기록을 조회합니다.

현재 반환율 같은 연도별 고급 통계 화면은 없습니다. 과거 물품·요청·처리 이력 조회를 제공하며, 없는 통계를 임의 수치로 표시하지 않습니다.

## 배포 전 필수 확인

- 실제 Supabase에서 001~008 migration·private 버킷·직접 접근 차단 확인
- 이름/학번/PIN 가입·로그인·연속 실패 제한 확인
- 부장/회장단 승인 및 일반 임원 학생증 열람 거부 확인
- 승인·거절 시 Storage 객체 삭제, 삭제 장애 후 재시도 확인
- 두 기기에서 같은 슬롯 예약 경쟁 및 다른 학생 요청 접근 차단 확인
- 미수령·재예약·반환 완료·코드 재사용 차단 확인
- 5분 작업 스케줄과 실패 감시 연결
- 사진의 개인정보 가림, 운영 안내·보존기간·문의 담당자 확정
- Vercel에 서버 환경변수 설정, APP_ORIGIN과 실제 HTTPS 주소 일치 확인

Vercel에서는 기존 Next.js 프로젝트를 연결하고 `npm run build`를 사용합니다. 실서비스 URL·DB·Storage가 연결되지 않은 현재 코드을 학생들에게 운영 서비스로 안내하면 안 됩니다.

## 주요 파일

- `components/app.tsx`: 기존 레이아웃 기반 화면·폼·권한별 메뉴
- `components/provider.tsx`: 서버 데이터 조회와 실제 요청 처리. Mock state 제거
- `lib/model.ts`: 지정 카테고리·장소·수령 장소·화면 타입
- `lib/server/`: DB·PIN·세션·파일 업로드·삭제 처리
- `app/api/`: 인증·화면 데이터·업무 처리·권한 검증 이미지·주기 작업
- `supabase/migrations/20260922000*.sql`: 기존 001을 확장하는 운영 migration
- `tests/`: 격리된 DB/브라우저 테스트. 운영에서 import하지 않음
- `docs/CHANGE_REPORT.md`: 유지·수정·연결·삭제 분류 및 남은 작업

## 현재 공개 화면과 운영 서버

`npm run build`는 기존 Next.js 운영 앱과, 같은 컴포넌트·CSS를 재사용하는 `dist` 공개 화면을 함께 생성합니다. Sites에는 후자만 배포합니다. 공개 화면의 `publicReadiness` 모드는 API 호출이나 개인정보 수집 없이 운영 연결 대기를 표시합니다. 이 모드는 Supabase 연결 여부를 가장하지 않으며 가짜 레코드가 없습니다. 실제 운영은 위 환경변수·migration·최초 운영자·정기 실행을 적용한 Next.js 서버를 배포해야 합니다. 공개 화면에 키를 넣는 것으로 운영이 활성화되지는 않습니다.

## 관리자 직접 접수

‘관리 → 분실물 직접 등록’은 학생복지부·회장단·SUPER_ADMIN만 사용합니다. 사진·물품명·종류·발견 장소/세부 위치/날짜/시간·색상·브랜드·공개 특징·내부 보관번호를 입력하고 실물 및 개인정보 가림을 확인합니다. 서버가 업로드 소유자와 역할을 재검증하고, 접수·공식 물품·사진·보관번호·처리 이력을 한 트랜잭션으로 기록합니다. 실패 시 일부만 공개되지 않습니다. 내부 보관번호는 학생 조회 응답에 포함하지 않습니다.

장소 관리는 회장단/최고 관리자만 지정된 17개 장소의 사용 여부를 설정합니다. 임의 장소를 추가하지 않고 ‘기타’는 유지하며 이전 발견 장소 기록도 보존합니다.

## 새 Supabase 키 설정 (2026-09-26)

새 설치는 `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`, `SUPABASE_SECRET_KEY`를 사용합니다. 서버 키는 `sb_secret_` 형식이며 로컬 `.env.local` 및 운영 서버의 비밀 환경변수에만 입력합니다. 대시보드의 복사 위치와 체크리스트는 [SUPABASE_SETUP.md](docs/SUPABASE_SETUP.md)의 B 항목을 따르세요.

이전 `SUPABASE_SERVICE_ROLE_KEY`는 새 변수가 없을 때만 호환 지원합니다. 두 변수의 값이 다르면 연결을 거부합니다. 이번 변경에 SQL 재실행은 필요하지 않습니다. 최초 빈 프로젝트는 기존 `production-fresh.sql`을 한 번 실행합니다.
